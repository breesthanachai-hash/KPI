# People Pulse — KPI, Skill & Employee Portal

People Pulse คือระบบจัดการงาน ผลงาน KPI สกิล การเติบโต ระบบ Points และรางวัล รวมถึงข้อมูลบุคลากรสำหรับทีมหน้าบ้านและการเติบโต (Growth-Commerce) โดยมีพื้นที่ทำงานแยกตามสิทธิ์ของ HR / Admin, หัวหน้าทีม และพนักงาน

## ภาพรวมระบบล่าสุด

- UI พื้นสว่างโทนฟ้า–ส้ม ใช้ Noto Sans Thai ให้ตัวอักษรและสถานะอ่านง่าย รองรับเดสก์ท็อปและมือถือ ไม่ใช่ธีมอวกาศหรือไซเบอร์แบบเดิม
- เปิดระบบมาที่งานเป็นหลัก มี Today's Focus, รายการงาน, Kanban, งานเกินกำหนด, งานรอตรวจ และ Project Pulse
- รองรับงาน รีเควสต์ และภารกิจ พร้อมหลักฐานเป็นลิงก์หรือไฟล์ ผู้ตรวจอนุมัติหรือส่งกลับแก้ไขได้ และมอบ Points สำหรับงานหลังหลักฐานผ่านเท่านั้น
- Employee Work Portfolio รวมงานที่เสร็จ หลักฐาน ผู้ตรวจ คะแนน และไฟล์ย้อนหลัง พร้อมค้นหา กรอง และส่งออก CSV
- แบบประเมิน KPI และสมรรถนะตามตำแหน่ง บันทึกแยกตามรอบ พร้อม Skill Profile, Talent Fit, OVR, Power Arena และแผนพัฒนา
- People Operating System รองรับเวลาเข้า–ออก มาสาย ขาดงาน วันลา การอนุมัติ เงินเดือน กรอบค่าจ้าง Skill-based Pay และ Action Center
- People AI ช่วยวิเคราะห์งาน KPI สกิล และวิธีใช้ระบบในพื้นที่ของผู้ดูแล โดยอ้างอิงข้อมูลที่ผู้ใช้มีสิทธิ์เห็น
- ระบบกฎองค์กรแบบร่าง–ประกาศ–ออกเวอร์ชันใหม่ พร้อมกำหนดขอบเขต วันมีผล และหลักฐานการรับทราบของพนักงาน
- ศูนย์เอกสารองค์กรแยกจากกฎองค์กร รองรับสัญญาและไฟล์ HR ที่เก็บแบบจำกัดสิทธิ์ พร้อมแม่แบบ DOCX สำหรับเริ่มจัดทำเอกสาร
- แฟ้มพนักงานมีประวัติใบเตือนแบบตรวจย้อนหลังได้ และเกียรติบัตรหรือรางวัลจากผลงาน พร้อมไฟล์หลักฐานและสถานะ
- พนักงานสมัครบัญชีด้วยอีเมล ID รหัสผ่าน ชื่อ–นามสกุล และชื่อเล่นได้จากหน้า Login โดยบัญชีจะยังเข้าใช้ไม่ได้จนกว่า HR / Admin จะตรวจและผูกกับโปรไฟล์พนักงานที่ใช้งานอยู่
- หน้า **ผู้ใช้งานและสิทธิ์** ของ Admin มีแท็บฐานข้อมูลผู้ใช้ คำขอสมัครใหม่ และกฎสิทธิ์ พร้อมส่งออกรายการผู้ใช้เป็น CSV สำหรับเปิดใน Excel โดยไม่ส่งออก Password Hash, Salt หรือ Session Token
- ระบบ Points และรางวัลใช้กติกาที่ประกาศอยู่เป็นแหล่งข้อมูลหลัก มีเพดานรายเดือน หลักฐาน สิทธิ์ผู้บันทึก การป้องกันรายการซ้ำ และประวัติตรวจสอบย้อนหลัง

## ทีม Growth-Commerce: 8 ตำแหน่ง

ตำแหน่งที่ใช้งานปัจจุบันอยู่ในแผนก `growth-commerce` เดียวกัน ส่วนเทมเพลตตำแหน่งเดิมยังคงไว้เพื่ออ่านข้อมูลเก่าที่มีอยู่แล้ว

1. ผู้จัดการทีมหน้าบ้านและการเติบโต
2. นักการตลาดด้าน Customer Insight
3. นักการตลาดด้าน Offer & Conversion
4. นักการตลาดด้าน CRM & Retention
5. นักตัดต่อวิดีโอสาย Performance
6. นักตัดต่อวิดีโอสาย Brand & Content
7. ผู้ดูแล TikTok Shop / Shopee / Lazada
8. ผู้เชี่ยวชาญโฆษณา Facebook

แต่ละตำแหน่งมี KPI, เป้าหมาย, สกิลเฉพาะงาน, ระดับเป้าหมาย และตัวอย่างหลักฐานที่เหมาะกับงานจริงของตำแหน่งนั้น

## KPI, สมรรถนะ และ AI Mastery

คะแนนประเมินรวมใช้สูตร `KPI 70% + Skill 30%` โดย KPI ของแต่ละตำแหน่งมีน้ำหนักรวม 100% และ Skill Score มาจาก 6 หมวดดังนี้

| หมวดสมรรถนะ | น้ำหนัก |
| --- | ---: |
| สกิลตามตำแหน่ง | 35% |
| การใช้ AI ในการทำงาน | 10% |
| การทำงานและความรับผิดชอบ | 20% |
| การทำงานกับผู้อื่น | 15% |
| ความเป็นมืออาชีพ | 10% |
| การเติบโตและพัฒนาตน | 10% |

แต่ละตำแหน่งประเมินรวม 22–24 สมรรถนะ ระดับ 1–5 และมี AI Mastery เป็นเส้นทางเดียวกันทั้งทีม

- ระดับ 1–2: ใช้ AI ตามตัวอย่าง เขียน Prompt พร้อมบริบท ไม่ส่งข้อมูลลับ และตรวจคำตอบก่อนใช้
- ระดับ 3: นำ AI เข้า Workflow ของตำแหน่งครบขั้น พร้อมวัดเวลา คุณภาพ หรือผลลัพธ์
- ระดับ 4: สร้าง Prompt Template หรือ Automation ที่ใช้ซ้ำได้ มีการทดสอบคุณภาพและควบคุมความเสี่ยง
- ระดับ 5: ออกแบบมาตรฐาน AI ของทีม โค้ชผู้อื่น และเชื่อมผลลัพธ์กับธุรกิจอย่างตรวจสอบได้

หลักฐาน AI ถูกปรับตามตำแหน่ง เช่น Insight, Offer, CRM, Video Workflow, Marketplace, Forecast หรือ Media Buying และกำหนดให้มี Human Review เมื่อกระทบงบ ลูกค้า ข้อมูล หรือการตัดสินใจสำคัญ

AI Mastery ใช้ประกอบคะแนนสมรรถนะและแผนพัฒนา แต่ไม่เปิดสิทธิ์เงินเพิ่มตามสกิลโดยอัตโนมัติ

สูตร OVR ใช้ค่าพลังจากสกิลและงาน 70% ร่วมกับ KPI 30% และจำกัดคะแนนสูงสุดที่ 99 ส่วน Growth & Reward Path ใช้ KPI 40%, สกิล 40%, เควสต์ 15% และความสม่ำเสมอ 5%

## สิทธิ์ใช้งานและ Employee Portal

- **HR / Admin** จัดการข้อมูลทั้งหมด บัญชีผู้ใช้ แฟ้มพนักงาน เงินเดือน เอกสาร สัญญา การประเมิน Points รางวัล และกฎองค์กร
- **หัวหน้าทีม** เห็นเฉพาะสมาชิก งาน โปรเจกต์ ผลประเมิน และหลักฐานในแผนกที่ได้รับมอบหมาย โดยไม่เปิดข้อมูลส่วนตัว เอกสารสมัครงาน หรือเงินเดือน
- **พนักงาน** ใช้ MY PEOPLE PULSE เพื่อดูและจัดการเฉพาะข้อมูลของตนเอง ได้แก่ งาน แฟ้มผลงาน KPI/สกิล การเติบโต เงินเดือน Points รางวัล การแจ้งเตือน และกฎองค์กร รวมถึงสร้างงานประสานให้ตนเองหรือเพื่อนร่วมแผนกได้

พนักงานเริ่มงาน อัปเดตความคืบหน้า ส่งหลักฐานของงานที่ตนเองรับผิดชอบ ใช้ Points ของตนเอง ยืนยันรับทราบกฎ และลงนามสัญญาของตนเองได้ รวมทั้งสร้างรีเควสต์ให้ตนเองหรือพนักงานที่ยังใช้งานในแผนกเดียวกัน งานที่พนักงานสร้างจะถูกบังคับเป็นสถานะ “ต้องทำ” ความคืบหน้า 0% และ 0 Points ไม่นับเป็น KPI หรือภาระงานทางการ และมีเพดานงานเปิด 12 งานต่อผู้สร้าง 12 งานต่อผู้รับ และ 5 งานต่อคู่ผู้สร้าง–ผู้รับ เพื่อป้องกันการสร้างงานปั๊มคะแนนหรือปั่นสถานะภาระงาน ผู้รับงานเป็นผู้ส่งหลักฐาน และหัวหน้าหรือ HR เป็นผู้ตรวจ พนักงานแก้งานที่ส่งตรวจหรือปิดแล้วไม่ได้ หัวหน้าหรือ HR ส่งหลักฐานแทนพนักงานไม่ได้ และผู้ใช้ที่ผูกกับพนักงานเป้าหมายไม่สามารถประเมิน อนุมัติงาน หรือให้/หัก Points ตนเองได้ มุมมองสำนักงานและค่าพลังทีมแสดงเฉพาะข้อมูลสรุปที่ปลอดภัย ไม่เปิดรายละเอียดงานหรือข้อมูลส่วนตัวของผู้อื่น

ผู้ดูแลสามารถเปิดตัวอย่าง Employee Portal แบบอ่านอย่างเดียวได้ โดยไม่เปลี่ยนบัญชีจริงและไม่อนุญาตให้เริ่มงาน ส่งหลักฐาน แลกรางวัล รับทราบกฎ หรือเปลี่ยนสถานะการแจ้งเตือนจากโหมดทดลอง

### บัญชีแบบ ID + รหัสผ่าน

People Pulse ใช้บัญชีของระบบเอง ผู้ใช้จึง **ไม่ต้องมีบัญชี ChatGPT** และรหัสผู้ใช้ไม่จำเป็นต้องตรงกับอีเมล HR / Admin สร้างผู้ใช้จากหน้า **ผู้ใช้งานและสิทธิ์** โดยกำหนดข้อมูลให้ครบเป็น **รหัสผู้ใช้ + รหัสผ่านชั่วคราว + บทบาท + โปรไฟล์พนักงาน** (บทบาท Admin ไม่ต้องผูกโปรไฟล์) แล้วส่งรหัสให้เจ้าของบัญชีผ่านช่องทางส่วนตัว

- ผู้ใช้ต้องเปลี่ยนรหัสผ่านชั่วคราวทันทีในการเข้าใช้ครั้งแรก ก่อนเปิดข้อมูลหรืองานในระบบ
- ผู้ใช้เลือกตั้งเป็น PIN ตัวเลขอย่างเดียวอย่างน้อย 8 หลักได้ หรือใช้รหัสผ่านทั่วไปอย่างน้อย 15 ตัวอักษร
- บัญชี `manager` และ `employee` ต้องผูกกับโปรไฟล์พนักงานที่ยังใช้งานอยู่ สิทธิ์ถูกตรวจจากบทบาท สถานะ และแผนกปัจจุบันทุกคำขอ
- การรีเซ็ตรหัสผ่าน เปลี่ยนรหัสผู้ใช้ บทบาท สถานะ หรือโปรไฟล์ที่ผูก จะยกเลิกเซสชันเดิมของบัญชีนั้น ผู้ดูแลแก้ รีเซ็ต หรือพักบัญชีที่ตนกำลังใช้จากหน้าจัดการผู้ใช้ไม่ได้; ให้เปลี่ยนรหัสผ่านของตนจากเมนูโปรไฟล์
- เซสชันส่งผ่านคุกกี้ `HttpOnly`, `SameSite=Strict`, `Path=/` และใช้ `Secure` บน HTTPS โทเคนดิบไม่ถูกบันทึกใน D1 และไม่ถูกส่งคืนใน JSON
- คำขอที่แก้ข้อมูลต้องมาจาก Origin เดียวกับเว็บไซต์ ระบบไม่ใช้ CSRF token แยก และไม่อนุญาตให้ข้ามการตรวจสิทธิ์ด้วย localhost ใน production

## เอกสารองค์กร ใบเตือน และเกียรติบัตร

- หน้า **เอกสารองค์กร** เป็นพื้นที่ของ HR / Admin สำหรับเก็บสัญญาเช่า เอกสารการจ้าง เอกสาร HR เอกสารกฎหมาย การเงิน และการดำเนินงาน พร้อมเลขเอกสาร เวอร์ชัน เจ้าของเอกสาร วันมีผล วันหมดอายุ และสถานะ โดยใช้การเก็บถาวรแทนการลบประวัติ
- ไฟล์เอกสารจริงเก็บใน R2 และตรวจสิทธิ์ฝั่งเซิร์ฟเวอร์ทุกครั้งที่ดาวน์โหลด ผู้จัดการและพนักงานไม่ได้รับข้อมูลแฟ้มวินัยหรือไฟล์ส่วนตัวจากการเป็นสมาชิกทีม
- ระบบมีแม่แบบ DOCX 5 ฉบับ ได้แก่ สัญญาเช่าสำนักงาน สัญญาจ้างงาน ข้อตกลงรักษาความลับ หนังสือเตือนพนักงาน และแบบรับ–คืนทรัพย์สิน
- ทุกแม่แบบเป็น **ฉบับร่าง** เพื่อช่วยจัดเตรียมเอกสาร ไม่ใช่คำปรึกษากฎหมาย ต้องกรอกข้อมูล ตรวจข้อเท็จจริง อำนาจลงนาม และให้ HR หรือที่ปรึกษากฎหมายทบทวนก่อนใช้จริง
- ประวัติใบเตือนแยกสถานะ `draft → issued → acknowledged / resolved / withdrawn` ใช้ revision ป้องกันการแก้ชนกัน และเก็บเหตุการณ์ย้อนหลัง การลงชื่อรับทราบหมายถึงได้รับเอกสาร ไม่ใช่ยอมรับผิด และการออกใบเตือนไม่หัก Points อัตโนมัติ
- เกียรติบัตรและรางวัลจากผลงานรองรับใบรับรอง รางวัล เกียรติยศ การอบรม และใบอนุญาต พร้อมผู้ออก วันที่ได้รับ วันหมดอายุ รหัสรับรอง ลิงก์ตรวจสอบ และไฟล์หลักฐาน

## กฎองค์กรและการรับทราบ

- HR / Admin สร้างร่าง ตรวจรายการก่อนประกาศ และกำหนดหมวดกับวันที่มีผลได้ ปัจจุบันหน้าใช้งานตั้งค่าเป็นทั้งองค์กร; ชั้นข้อมูลรองรับขอบเขตแผนก ตำแหน่ง และประเภทการจ้างสำหรับการขยายระบบภายหลัง
- พนักงานเห็นเฉพาะฉบับที่ประกาศแล้ว มีผลอยู่ และตรงกับขอบเขตของตนเอง
- ฉบับที่ประกาศแล้วแก้ตรง ๆ ไม่ได้ การแก้ไขจะสร้างเวอร์ชันถัดไปและปิดช่วงมีผลของฉบับก่อนหน้า
- ใบรับทราบผูกกับพนักงาน บัญชี เวอร์ชัน และ hash ของเนื้อหา จึงตรวจสอบได้ว่ารับทราบข้อความฉบับใด และไม่สร้างรายการซ้ำในเวอร์ชันเดียวกัน
- มีแม่แบบข้อบังคับการทำงานพร้อม checklist 8 หัวข้อ, กติกา Points และรางวัล และนโยบายการใช้ AI/ข้อมูล
- การรับทราบหมายถึงยืนยันว่าได้อ่านเอกสาร ไม่ใช่การสละสิทธิ์ และระบบช่วยตรวจความครบถ้วนของแม่แบบเท่านั้น HR ยังต้องทบทวนข้อกฎหมายก่อนประกาศใช้จริง

## กติกา Points แบบสมดุล

กติกาด้านล่างคือค่าเริ่มต้นของนโยบาย `points-and-rewards` ที่ประกาศอยู่ ระบบคำนวณจากกติกาของเวอร์ชันที่มีผล และเก็บที่มาของรายการไว้ตรวจสอบย้อนหลัง

วันและเดือนของงาน Points และคำขอแลกรางวัลอ้างอิงเขตเวลา `Asia/Bangkok` เพื่อให้รายการช่วงหลังเที่ยงคืนของไทยไม่ถูกนับย้อนเข้าเดือน UTC ก่อนหน้า

### สูตรและเพดานหลัก

| รายการ | กติกาเริ่มต้น |
| --- | --- |
| ผลประเมินประจำเดือน | ต้องได้อย่างน้อย 70 คะแนน; `(คะแนนรวม − 60) × 6`; สูงสุด 240 Points ต่อเดือน |
| Points จากงานที่ผ่านหลักฐาน | รวมไม่เกิน 420 Points ต่อเดือน และให้ครั้งเดียวต่อแหล่งงาน |
| เข้างานตรงเวลา | +5 Points ต่อวัน สูงสุด 22 วัน หรือ 110 Points ต่อเดือน |
| ส่งก่อนกำหนด / ตรงกำหนด | +25 / +15 Points; โบนัสกำหนดส่งรวมไม่เกิน 80 Points ต่อเดือน |
| โบนัสพิเศษ / เควสต์ | +50 / +75 Points ต้องมีหลักฐาน และแต่ละประเภทไม่เกิน 2 ครั้ง/เดือน |
| Points บวกมาตรฐานนอกผลประเมิน | รวมไม่เกิน 900 Points ต่อเดือน |
| Points ลบ | รวมไม่เกิน 200 Points ต่อเดือน; ลาที่อนุมัติแล้ว 0 Points |
| การแลกรางวัล | ไม่เกิน 2 ครั้ง/เดือน เว้นอย่างน้อย 7 วัน ยอดคงเหลือต้องไม่ติดลบ และต้องรับทราบกติกา Points ฉบับปัจจุบันก่อน |

ตัวอย่าง: คะแนนประเมินรวม 85 คะแนน ได้ `(85 − 60) × 6 = 150` Points

### Points ตามประเภทงานและความสำคัญ

Points จะเข้าหลังผู้มีสิทธิ์อนุมัติหลักฐานแล้วเท่านั้น หากชนเพดาน ระบบยังปิดงานได้แต่จะไม่ให้ Points บางส่วน

| ประเภท | ทั่วไป | ปานกลาง | สำคัญ | เร่งด่วน |
| --- | ---: | ---: | ---: | ---: |
| งาน | 10 | 20 | 35 | 50 |
| รีเควสต์ | 15 | 25 | 40 | 60 |
| ภารกิจ | 40 | 60 | 90 | 120 |

รายการลบเริ่มต้น ได้แก่ มาสาย −20, ขาดงานที่ตรวจสอบแล้ว −120, งานผิดพลาดพร้อมหลักฐาน −40, ใบเตือน −150 และผิดกฎ −100 โดยรายการวินัยทำได้เฉพาะ HR หลังตรวจข้อเท็จจริง ไม่ใช้ Points แทนกระบวนการวินัยหรือสิทธิอุทธรณ์ และหัวหน้าให้หรือหัก Points ตนเองไม่ได้

ระบบตรวจยอดคงเหลือ สต็อก จำนวนครั้ง ช่วงพัก และการรับทราบกติกาก่อนสร้างคำขอแลก จากนั้น HR เปลี่ยนสถานะตามลำดับ `รออนุมัติ → อนุมัติ → ส่งมอบแล้ว` หรือยกเลิกได้ก่อนส่งมอบ การหัก Points ใช้รายการใน ledger และการยกเลิกจะคืน Points กับสต็อกเพียงครั้งเดียวด้วยรายการย้อนกลับแทนการลบประวัติเดิม

## โครงสร้างข้อมูล

ข้อมูลหลักเก็บใน Cloudflare D1 ผ่าน Drizzle ORM และไฟล์เอกสารเก็บใน Cloudflare R2

- `employees`, `employee_profiles`, `hr_profiles` — ทะเบียนพนักงาน ข้อมูลส่วนตัว การจ้าง และค่าตอบแทน
- `user_accounts`, `auth_credentials`, `auth_sessions`, `auth_rate_limits`, `auth_events`, `notification_reads` — บัญชีและการผูกพนักงาน รหัสผ่านแบบ hash เซสชันแบบ hash-only การจำกัดการลองเข้าใช้ เหตุการณ์ความปลอดภัย และสถานะอ่านการแจ้งเตือน
- `employee_registration_requests`, `employee_registration_review_claims` — คำขอสมัครพนักงาน รหัสผ่านที่ hash ตั้งแต่รับคำขอ และตัวล็อกการอนุมัติหรือปฏิเสธไม่ให้ทำซ้ำ
- `evaluations`, `skill_achievements`, `talent_actions` — ผล KPI/สกิล ระดับที่ยืนยันแล้ว เงินเพิ่ม และแผนพัฒนา
- `attendance_records` — เวลาเข้า–ออก มาสาย ขาดงาน วันลา และประวัติการอนุมัติ
- `projects`, `work_items`, `work_submissions` — โปรเจกต์ งาน ความคืบหน้า หลักฐาน และผลตรวจ
- `point_ledger`, `point_events`, `point_mutation_claims`, `point_cap_claims` — ยอดเคลื่อนไหว เหตุการณ์ หลักฐาน snapshot กฎที่ใช้ และตัวล็อกเพดาน Points
- `rewards`, `reward_redemptions`, `reward_redemption_claims` — แคตตาล็อก สต็อก คำขอแลก และตัวกันคำขอหรือการตัดสต็อกซ้ำ
- `organization_policies`, `organization_policy_publish_claims` — เนื้อหา เวอร์ชัน ช่วงมีผล ขอบเขต กติกา hash และตัวกันการประกาศชนกัน
- `policy_acknowledgements` — หลักฐานการรับทราบที่ผูกพนักงาน บัญชี เวอร์ชัน และ content hash
- `application_documents`, `employment_contracts` — เอกสารสมัครงาน สัญญาหลายเวอร์ชัน คำยินยอม และลายเซ็นอิเล็กทรอนิกส์
- `organization_documents` — คลังสัญญาและเอกสารองค์กรพร้อม metadata, revision และไฟล์ R2 แบบจำกัดสิทธิ์
- `employee_warnings`, `employee_warning_events` — ประวัติใบเตือน สถานะ และ audit trail แบบไม่ลบย้อนหลัง
- `employee_recognitions` — เกียรติบัตร รางวัล การอบรม และหลักฐานที่ผูกกับแฟ้มพนักงาน

## เปิดใช้จริงอย่างปลอดภัย

Production จะ **ไม่เติมข้อมูลตัวอย่างอัตโนมัติ** ค่าเริ่มต้นของ `PEOPLE_PULSE_ENABLE_DEMO_DATA` คือปิด และควรเปิดเป็น `true` เฉพาะฐานทดลองที่แยกจากข้อมูลจริงเท่านั้น ข้อมูลตัวอย่างที่เคยอยู่ใน D1 เดิมจะไม่ถูกลบเอง ให้สำรองและล้างหรือย้ายโดยได้รับการยืนยันจากเจ้าของข้อมูลก่อน

หน้า **ผู้ใช้งานและสิทธิ์** มี Launch Readiness Center ตรวจ 6 เรื่อง: ข้อมูลตัวอย่าง, พนักงานจริง, กฎที่ผ่านการทบทวน, บัญชีที่ผูกกับโปรไฟล์, การเข้าใช้ครั้งแรก และเส้นทางเอกสาร/หลักฐานจริง ระบบนี้แสดงสถานะเท่านั้นและไม่ลบข้อมูลแทน HR

ลำดับแนะนำสำหรับ pilot ทีม Growth-Commerce 8 คน:

1. สำรอง D1/R2 และยืนยันว่าจะล้างหรือเก็บฐาน demo แยก
2. นำเข้ารายชื่อ อีเมล ตำแหน่ง ผู้จัดการ และค่าตอบแทนจริง
3. ให้ HR/ฝ่ายกฎหมายแก้แม่แบบกฎองค์กร แล้วประกาศเวอร์ชันจริง
4. เลือกวิธีเริ่มบัญชี: ให้ HR สร้างรหัสผู้ใช้และรหัสชั่วคราว หรือให้พนักงานกรอกใบสมัครหน้า Login แล้ว HR ตรวจคำขอและผูกกับโปรไฟล์พนักงานที่ใช้งานอยู่ก่อนอนุมัติ
5. ให้ HR 1 คน หัวหน้า 1 คน และพนักงาน 2–3 คนทดสอบมอบหมายงาน → ส่งหลักฐาน → ตรวจ → ได้ Points → แลกรางวัล รวมถึงอ่านและลงนามสัญญา
6. ทดลอง 3–5 วัน ตรวจข้อมูลและสิทธิ์ แล้วจึงเชิญสมาชิกที่เหลือ

การเปิดทั้งบริษัทต้องเพิ่มตำแหน่ง KPI สกิล และกรอบเงินเดือนของ Telesales, Accounting และทีมผลิต/แพ็ก/ขนส่งก่อน เพราะเวอร์ชันปัจจุบันออกแบบ pilot สำหรับทีม Growth-Commerce 8 ตำแหน่ง

### สร้าง Admin เริ่มต้นและตั้งค่า Auth

สร้างรหัสชั่วคราว 20 ตัว ตัวตรวจรหัสที่ hash แล้ว และ secrets สำหรับ production ด้วยคำสั่งนี้ (อย่าส่งรหัสผ่านจริงผ่าน command line):

```bash
npm run auth:bootstrap -- --login-id admin --email owner@example.com --name "ชื่อผู้ดูแล"
```

ผลลัพธ์ JSON แสดงรหัสชั่วคราวเพียงครั้งเดียว ให้เก็บรหัสนั้นใน password manager และกำหนดค่า `environment` ที่สคริปต์สร้างไว้ใน environment ของเครื่องหรือ OpenAI Sites:

- `PEOPLE_PULSE_PASSWORD_PEPPER_VERSION` และ `PEOPLE_PULSE_PASSWORD_PEPPER_V1` — เวอร์ชันและ secret สำหรับ hash รหัสผ่าน
- `PEOPLE_PULSE_RATE_LIMIT_SECRET` — secret คนละค่ากับ pepper สำหรับปกปิด key ของ rate limit
- `PEOPLE_PULSE_BOOTSTRAP_LOGIN_ID`, `PEOPLE_PULSE_BOOTSTRAP_PASSWORD_HASH`, `PEOPLE_PULSE_BOOTSTRAP_ADMIN_EMAIL` และ `PEOPLE_PULSE_BOOTSTRAP_ADMIN_NAME` — บัญชี Admin แรก โดยสามค่าหลักต้องกำหนดครบหรือไม่กำหนดเลย
- `PEOPLE_PULSE_CANONICAL_ORIGIN=https://peoplepulse.profaiprofit.com` — Origin หลักที่อนุญาตใน production

ระบบใช้ `PBKDF2-SHA-256` แบบต่อเนื่อง 6 ช่วงผ่าน `node:crypto` ช่วงละ **100,000 รอบ** รวมงาน **600,000 รอบ** สำหรับรหัสใหม่ การรีเซ็ต และการเปลี่ยนรหัสทุกครั้ง รูปแบบปัจจุบันชื่อ `pbkdf2-sha256-chain-v1` เพื่อไม่ให้สับสนกับ PBKDF2 แบบช่วงเดียว ตัวตรวจรหัสยอมรับเพียง 2 รูปแบบตายตัว: รูปแบบปัจจุบันรวม 600,000 รอบ และ credential เก่า `pbkdf2-sha256` 100,000 รอบระหว่างการบังคับเปลี่ยนรหัสเท่านั้น วิธีแบ่งช่วงนี้จำเป็นเพราะ Worker จำกัด PBKDF2 หนึ่งคำสั่งไม่เกิน 100,000 รอบ ค่าอื่นหรือการจับคู่ algorithm/จำนวนรอบที่ไม่ตรงนโยบายจะถูกปฏิเสธก่อนเริ่มคำนวณ

ห้าม commit ค่าเหล่านี้หรือไฟล์ `.dev.vars` ลง Git; repository ignore `.dev.vars*` และยอมให้ commit ได้เฉพาะ `.dev.vars.example` ที่ไม่มี secret ห้ามสร้างค่า `PEOPLE_PULSE_PASSWORD_PEPPER_V1` ใหม่ทับของเดิมเมื่อมีผู้ใช้แล้ว เพราะรหัสผ่านเดิมจะตรวจไม่ได้ การหมุน pepper ต้องเก็บเวอร์ชันเก่าไว้จนกว่าจะเปลี่ยนรหัสผ่านครบทุกบัญชี

`0017_legacy_bootstrap_repair.sql` และเงื่อนไขซ่อมใน runtime คงไว้เพื่อรองรับประวัติการอัปเกรดที่ทำไปแล้วเท่านั้น คำสั่ง `--repair-existing` ถูกยกเลิกและสคริปต์จะหยุดโดยไม่สร้าง verifier หรือ secret ใหม่ บัญชีเดิมต้องเข้าสู่ระบบด้วยรหัสชั่วคราวเดิม แล้วเปลี่ยนรหัสผ่านผ่านหน้าบังคับเปลี่ยนรหัส ระบบจะเขียน credential แบบ chain รวม 600,000 รอบด้วย compare-and-swap, เพิ่ม credential version, เพิกถอน session เก่า และบันทึก audit ในขั้นตอนที่ตรวจสอบได้ ห้ามแก้ hash, salt, iteration หรือ credential version ใน D1 ด้วยมือ

การสร้าง bootstrap บนฐานใหม่ยอมรับเฉพาะ verifier `pbkdf2-sha256-chain-v1` รวม 600,000 รอบจาก generator รุ่นปัจจุบัน หากนำ bootstrap hash เก่า 100,000 รอบไปใช้กับฐานที่ยังไม่มี credential ระบบจะหยุดก่อนสร้างบัญชีหรือ credential ส่วนฐานที่มี credential 100,000 รอบอยู่แล้วจะตรวจรหัสเดิมได้ชั่วคราวเพื่อพาเจ้าของไปยังหน้าบังคับเปลี่ยนรหัสเท่านั้น

ก่อนเปิด Sites เป็น `public` ให้คำสั่งแรกคืน 0 แถว เพื่อยืนยันว่าบัญชี active ทุกบัญชีใช้ค่าปัจจุบัน และให้คำสั่งที่สองคืน 0 แถว เพื่อยืนยันว่าเจ้าของระบบเปลี่ยนรหัสชั่วคราวเสร็จแล้ว:

```sql
SELECT credential.user_account_id, credential.password_algorithm, credential.password_iterations
FROM auth_credentials AS credential
INNER JOIN user_accounts AS account ON account.id = credential.user_account_id
WHERE account.status = 'active'
  AND (
    credential.password_algorithm <> 'pbkdf2-sha256-chain-v1'
    OR credential.password_iterations <> 600000
  );

SELECT credential.user_account_id, credential.password_iterations, credential.must_change_password
FROM auth_credentials AS credential
WHERE credential.user_account_id = 'user-owner'
  AND (
    credential.password_iterations <> 600000
    OR credential.must_change_password <> 0
  );
```

หากคำสั่งใดมีผลลัพธ์ ให้คงเว็บไว้ที่ `custom/private` และให้เจ้าของเข้าสู่ระบบด้วยรหัสชั่วคราวเดิมเพื่อเปลี่ยนรหัสก่อน ห้ามลดจำนวนรอบหรือสร้าง bootstrap hash ใหม่มาทับบัญชีเดิม

การเผยแพร่ผ่าน OpenAI Sites จะผูก D1 binding ชื่อ `DB` และ R2 binding ชื่อ `FILES` ตาม `.openai/hosting.json`

## Release runbook แบบไม่แตะ production อัตโนมัติ

คำสั่งนี้ตรวจ runtime, build, lint, contract tests, ไฟล์ Sites, migration และแม่แบบเอกสารที่ถูก package โดย **ไม่ deploy, ไม่แก้ D1 และไม่แก้ R2**:

```bash
npm run release:verify
```

ถ้าต้องการตรวจเฉพาะความพร้อมก่อน build ให้ใช้:

```bash
npm run release:preflight
```

Preflight จะหยุดทันทีเมื่อ Node ต่ำกว่า 22.13, binding ไม่ใช่ `DB`/`FILES`, migration ไม่ต่อเนื่อง หรือ environment ของคำสั่งเปิด `PEOPLE_PULSE_ENABLE_DEMO_DATA=true` การผ่าน preflight ไม่ได้ยืนยันสถานะของฐานข้อมูลหรือไฟล์บน production จึงยังต้องทำ checklist ด้านล่างด้วยคนที่ได้รับสิทธิ์

### Checklist สำรองข้อมูลก่อน release

1. กำหนดช่วงหยุดเขียนข้อมูลชั่วคราวและแจ้งผู้ใช้งานที่จะร่วมทดสอบ
2. ใช้หน้าจัดการ Sites ที่ได้รับสิทธิ์สร้าง snapshot/export ของ D1 และสำรองไฟล์ R2 โดยบันทึกวันเวลา ผู้ดำเนินการ และเวอร์ชันแอป ห้ามใช้สคริปต์ release ใน repository นี้ลบหรือย้ายข้อมูลจริง
3. บันทึกจำนวนแถวของตารางสำคัญ เช่น `employees`, `user_accounts`, `work_items`, `point_ledger`, `reward_redemptions`, `employment_contracts` และจำนวนไฟล์ R2 เพื่อใช้เทียบหลัง release
4. ทดลองอ่านไฟล์สำรองและ restore ลงฐานแยกที่ไม่ใช่ production อย่างน้อยหนึ่งครั้ง ห้ามทดลอง restore ทับฐานจริง
5. ยืนยันว่า production ไม่ได้ตั้ง `PEOPLE_PULSE_ENABLE_DEMO_DATA=true` และตัดสินใจเก็บหรือล้างข้อมูล demo หลังมี backup โดยให้เจ้าของข้อมูลอนุมัติแยกต่างหาก

### Checklist ก่อนอนุมัติเผยแพร่

1. ใช้ commit ที่ clean และผ่าน `npm run release:verify`
2. ตรวจว่า archive ที่จะบันทึกเป็น Sites version มาจาก commit เดียวกัน และมี `dist/server/index.js`, `dist/client`, `dist/.openai/hosting.json` และ `dist/.openai/drizzle`
3. คง access policy ของ Sites เป็น `custom/private` ระหว่างติดตั้ง migration `0016`–`0021`, ตั้ง Auth secrets และ deploy เวอร์ชันใหม่ตามลำดับ migration-first จากนั้นรัน public gate ด้านบนให้บัญชี active ทุกบัญชีใช้ 600,000 รอบ และให้เจ้าของเปลี่ยนรหัสชั่วคราวเสร็จก่อน ห้ามเปิด public ก่อนผ่านการทดสอบระบบเข้าใช้
4. ทดสอบผ่าน custom domain ว่าไม่มีเซสชันได้ 401, รหัสชั่วคราวได้ 428 และบังคับเปลี่ยนรหัส, ครั้งที่ 6 ของการลองรหัสผิดได้ 429 พร้อม `Retry-After`, ออกจากระบบแล้วเซสชันเดิมใช้ไม่ได้ และบัญชีต่างบทบาทเข้าข้อมูลข้ามขอบเขตได้ 403
5. ทดสอบทั้งการสร้างบัญชีโดย HR และการสมัครจากหน้า Login: ผู้สมัครต้องยังเข้าใช้ไม่ได้ก่อนอนุมัติ, Admin ต้องเห็นคำขอโดยไม่เห็นข้อมูลลับ, ผูกได้เฉพาะโปรไฟล์พนักงาน active ที่ยังไม่มีบัญชี และหลังอนุมัติจึงเข้าใช้ด้วย ID + รหัสผ่านที่ผู้สมัครตั้งไว้ได้
6. ทดสอบ HR, หัวหน้า และพนักงานจริงอย่างน้อยบทบาทละหนึ่งบัญชี: เข้าระบบ → เปลี่ยนรหัส (ถ้าถูกบังคับ) → มอบหมายงาน → ส่งหลักฐาน R2 → ตรวจงาน → ได้ Points หนึ่งครั้ง → แลกรางวัล
7. ทดสอบเอกสารส่วนตัวข้ามบัญชีให้ได้ 403, ดาวน์โหลดแม่แบบ DOCX ทั้ง 5 ฉบับ และตรวจว่า `/favicon.ico` เปลี่ยนไปใช้ `/favicon.svg` โดยไม่เป็น 404
8. ตรวจ custom domain/SSL, การ redirect จากโดเมน Sites เดิม, หน้าจอ Chrome และมือถือ แล้วตรวจ Worker logs ว่าไม่มี 5xx
9. **public cutover gate:** หลังเจ้าของระบบอนุมัติผล smoke test และยืนยันแผน rollbackเท่านั้น จึงเปลี่ยน Sites access เป็น `public`; จากนั้นทดสอบซ้ำว่า anonymous เห็นหน้า Login/สมัครสมาชิกเท่านั้น และ API ยังคงตอบ 401/403/428/429 ตามเงื่อนไขก่อนเชิญผู้ใช้เพิ่ม

`release:verify` จะไม่ทำสองขั้นตอนนี้แทน: การบันทึก/deploy Sites version และการเปลี่ยน access policy เป็น public

### Rollback ที่ปลอดภัย

1. หากพบปัญหา Auth หลังเปิด public ให้เปลี่ยน access policy กลับเป็น `custom/private` ก่อน แล้วหยุดการเขียนข้อมูลและบันทึกอาการ เวลา release version และตารางหรือไฟล์ที่ได้รับผลกระทบ
2. ถ้าเป็นปัญหาเฉพาะ UI/แอป ให้ย้อนกลับไป Sites version ก่อนหน้าได้เมื่อยืนยันแล้วว่า schema ปัจจุบันยัง backward-compatible ห้ามย้อนกลับไปเวอร์ชันที่พึ่งพา identity จาก Sites/ChatGPT ขณะที่ access ยังเป็น public
3. ถ้ามี migration หรือข้อมูลเสีย ห้ามรัน SQL ย้อนกลับและห้าม restore ทับ production แบบทันที ให้ restore backup ลงฐานแยก ตรวจความครบถ้วน แล้ววางแผนกู้คืนกับเจ้าของข้อมูลก่อน
4. ตรวจจำนวนแถว, Points ledger, สต็อกรางวัล, สัญญา และไฟล์ R2 หลังแก้ไข จากนั้นทำ smoke test สามบทบาทซ้ำก่อนเปิดเขียนข้อมูล
5. บันทึกผล rollback และเหตุผลที่เลือก app rollback หรือ data recovery ไว้ในประวัติ release ทุกครั้ง
