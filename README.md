# People Pulse — KPI, Skill & Employee Portal

People Pulse คือระบบจัดการงาน ผลงาน KPI สกิล การเติบโต ระบบ Points และรางวัล รวมถึงข้อมูลบุคลากรสำหรับทีมหน้าบ้านและการเติบโต (Growth-Commerce) โดยมีพื้นที่ทำงานแยกตามสิทธิ์ของ HR / Admin, หัวหน้าทีม และพนักงาน

## ภาพรวมระบบล่าสุด

- UI พื้นสว่างโทนฟ้า–ส้ม ใช้ Noto Sans Thai ให้ตัวอักษรและสถานะอ่านง่าย รองรับเดสก์ท็อปและมือถือ ไม่ใช่ธีมอวกาศหรือไซเบอร์แบบเดิม
- เปิดระบบมาที่งานเป็นหลัก มี Today's Focus, รายการงาน, Kanban, งานเกินกำหนด, งานรอตรวจ และ Project Pulse
- รองรับงาน รีเควสต์ และภารกิจ พร้อมหลักฐานเป็นลิงก์หรือไฟล์ ผู้ตรวจอนุมัติหรือส่งกลับแก้ไขได้ และมอบ Points สำหรับงานหลังหลักฐานผ่านเท่านั้น
- Employee Work Portfolio รวมงานที่เสร็จ หลักฐาน ผู้ตรวจ คะแนน และไฟล์ย้อนหลัง พร้อมค้นหา กรอง และส่งออก CSV
- แบบประเมิน KPI และสมรรถนะตามตำแหน่ง บันทึกแยกตามรอบ พร้อม Skill Profile, Talent Fit, OVR, Power Arena และแผนพัฒนา
- People Operating System รองรับเวลาเข้า–ออก มาสาย ขาดงาน วันลา การอนุมัติ เงินเดือน กรอบค่าจ้าง Skill-based Pay และ Action Center
- People AI ช่วยวิเคราะห์งาน KPI สกิล และวิธีใช้ระบบในพื้นที่ของผู้ดูแล โดยอ้างอิงข้อมูลที่ผู้ใช้มีสิทธิ์เห็น
- ระบบกฎองค์กรแบบร่าง–ประกาศ–ออกเวอร์ชันใหม่ พร้อมกำหนดขอบเขต วันมีผล และหลักฐานการรับทราบของพนักงาน
- ระบบ Points และรางวัลใช้กติกาที่ประกาศอยู่เป็นแหล่งข้อมูลหลัก มีเพดานรายเดือน หลักฐาน สิทธิ์ผู้บันทึก การป้องกันรายการซ้ำ และประวัติตรวจสอบย้อนหลัง

## ทีม Growth-Commerce: 8 ตำแหน่ง

ตำแหน่งที่ใช้งานปัจจุบันอยู่ในแผนก `growth-commerce` เดียวกัน ส่วนเทมเพลตตำแหน่งเดิมยังคงไว้เพื่ออ่านข้อมูลเก่าที่มีอยู่แล้ว

1. ผู้จัดการทีมหน้าบ้านและการเติบโต
2. นักการตลาดด้าน Customer Insight
3. นักการตลาดด้าน Offer & Conversion
4. นักการตลาดด้าน CRM & Retention
5. นักตัดต่อวิดีโอสาย Performance
6. นักตัดต่อวิดีโอสาย Brand & Content
7. ผู้ดูแล TikTok Shop / Shopee / Lazada
8. ผู้เชี่ยวชาญโฆษณา Facebook

แต่ละตำแหน่งมี KPI, เป้าหมาย, สกิลเฉพาะงาน, ระดับเป้าหมาย และตัวอย่างหลักฐานที่เหมาะกับงานจริงของตำแหน่งนั้น

## KPI, สมรรถนะ และ AI Mastery

คะแนนประเมินรวมใช้สูตร `KPI 70% + Skill 30%` โดย KPI ของแต่ละตำแหน่งมีน้ำหนักรวม 100% และ Skill Score มาจาก 6 หมวดดังนี้

| หมวดสมรรถนะ | น้ำหนัก |
| --- | ---: |
| สกิลตามตำแหน่ง | 35% |
| การใช้ AI ในการทำงาน | 10% |
| การทำงานและความรับผิดชอบ | 20% |
| การทำงานกับผู้อื่น | 15% |
| ความเป็นมืออาชีพ | 10% |
| การเติบโตและพัฒนาตน | 10% |

แต่ละตำแหน่งประเมินรวม 22–24 สมรรถนะ ระดับ 1–5 และมี AI Mastery เป็นเส้นทางเดียวกันทั้งทีม

- ระดับ 1–2: ใช้ AI ตามตัวอย่าง เขียน Prompt พร้อมบริบท ไม่ส่งข้อมูลลับ และตรวจคำตอบก่อนใช้
- ระดับ 3: นำ AI เข้า Workflow ของตำแหน่งครบขั้น พร้อมวัดเวลา คุณภาพ หรือผลลัพธ์
- ระดับ 4: สร้าง Prompt Template หรือ Automation ที่ใช้ซ้ำได้ มีการทดสอบคุณภาพและควบคุมความเสี่ยง
- ระดับ 5: ออกแบบมาตรฐาน AI ของทีม โค้ชผู้อื่น และเชื่อมผลลัพธ์กับธุรกิจอย่างตรวจสอบได้

หลักฐาน AI ถูกปรับตามตำแหน่ง เช่น Insight, Offer, CRM, Video Workflow, Marketplace, Forecast หรือ Media Buying และกำหนดให้มี Human Review เมื่อกระทบงบ ลูกค้า ข้อมูล หรือการตัดสินใจสำคัญ

AI Mastery ใช้ประกอบคะแนนสมรรถนะและแผนพัฒนา แต่ไม่เปิดสิทธิ์เงินเพิ่มตามสกิลโดยอัตโนมัติ

สูตร OVR ใช้ค่าพลังจากสกิลและงาน 70% ร่วมกับ KPI 30% และจำกัดคะแนนสูงสุดที่ 99 ส่วน Growth & Reward Path ใช้ KPI 40%, สกิล 40%, เควสต์ 15% และความสม่ำเสมอ 5%

## สิทธิ์ใช้งานและ Employee Portal

- **HR / Admin** จัดการข้อมูลทั้งหมด บัญชีผู้ใช้ แฟ้มพนักงาน เงินเดือน เอกสาร สัญญา การประเมิน Points รางวัล และกฎองค์กร
- **หัวหน้าทีม** เห็นเฉพาะสมาชิก งาน โปรเจกต์ ผลประเมิน และหลักฐานในแผนกที่ได้รับมอบหมาย โดยไม่เปิดข้อมูลส่วนตัว เอกสารสมัครงาน หรือเงินเดือน
- **พนักงาน** ใช้ MY PEOPLE PULSE เพื่อดูและจัดการเฉพาะข้อมูลของตนเอง ได้แก่ งาน แฟ้มผลงาน KPI/สกิล การเติบโต เงินเดือน Points รางวัล การแจ้งเตือน และกฎองค์กร รวมถึงสร้างงานประสานให้ตนเองหรือเพื่อนร่วมแผนกได้

พนักงานเริ่มงาน อัปเดตความคืบหน้า ส่งหลักฐานของงานที่ตนเองรับผิดชอบ ใช้ Points ของตนเอง ยืนยันรับทราบกฎ และลงนามสัญญาของตนเองได้ รวมทั้งสร้างรีเควสต์ให้ตนเองหรือพนักงานที่ยังใช้งานในแผนกเดียวกัน งานที่พนักงานสร้างจะถูกบังคับเป็นสถานะ “ต้องทำ” ความคืบหน้า 0% และ 0 Points ไม่นับเป็น KPI หรือภาระงานทางการ และมีเพดานงานเปิด 12 งานต่อผู้สร้าง 12 งานต่อผู้รับ และ 5 งานต่อคู่ผู้สร้าง–ผู้รับ เพื่อป้องกันการสร้างงานปั๊มคะแนนหรือปั่นสถานะภาระงาน ผู้รับงานเป็นผู้ส่งหลักฐาน และหัวหน้าหรือ HR เป็นผู้ตรวจ พนักงานแก้งานที่ส่งตรวจหรือปิดแล้วไม่ได้ หัวหน้าหรือ HR ส่งหลักฐานแทนพนักงานไม่ได้ และผู้ใช้ที่ผูกกับพนักงานเป้าหมายไม่สามารถประเมิน อนุมัติงาน หรือให้/หัก Points ตนเองได้ มุมมองสำนักงานและค่าพลังทีมแสดงเฉพาะข้อมูลสรุปที่ปลอดภัย ไม่เปิดรายละเอียดงานหรือข้อมูลส่วนตัวของผู้อื่น

ผู้ดูแลสามารถเปิดตัวอย่าง Employee Portal แบบอ่านอย่างเดียวได้ โดยไม่เปลี่ยนบัญชีจริงและไม่อนุญาตให้เริ่มงาน ส่งหลักฐาน แลกรางวัล รับทราบกฎ หรือเปลี่ยนสถานะการแจ้งเตือนจากโหมดทดลอง

## กฎองค์กรและการรับทราบ

- HR / Admin สร้างร่าง ตรวจรายการก่อนประกาศ และกำหนดหมวดกับวันที่มีผลได้ ปัจจุบันหน้าใช้งานตั้งค่าเป็นทั้งองค์กร; ชั้นข้อมูลรองรับขอบเขตแผนก ตำแหน่ง และประเภทการจ้างสำหรับการขยายระบบภายหลัง
- พนักงานเห็นเฉพาะฉบับที่ประกาศแล้ว มีผลอยู่ และตรงกับขอบเขตของตนเอง
- ฉบับที่ประกาศแล้วแก้ตรง ๆ ไม่ได้ การแก้ไขจะสร้างเวอร์ชันถัดไปและปิดช่วงมีผลของฉบับก่อนหน้า
- ใบรับทราบผูกกับพนักงาน บัญชี เวอร์ชัน และ hash ของเนื้อหา จึงตรวจสอบได้ว่ารับทราบข้อความฉบับใด และไม่สร้างรายการซ้ำในเวอร์ชันเดียวกัน
- มีแม่แบบข้อบังคับการทำงานพร้อม checklist 8 หัวข้อ, กติกา Points และรางวัล และนโยบายการใช้ AI/ข้อมูล
- การรับทราบหมายถึงยืนยันว่าได้อ่านเอกสาร ไม่ใช่การสละสิทธิ์ และระบบช่วยตรวจความครบถ้วนของแม่แบบเท่านั้น HR ยังต้องทบทวนข้อกฎหมายก่อนประกาศใช้จริง

## กติกา Points แบบสมดุล

กติกาด้านล่างคือค่าเริ่มต้นของนโยบาย `points-and-rewards` ที่ประกาศอยู่ ระบบคำนวณจากกติกาของเวอร์ชันที่มีผล และเก็บที่มาของรายการไว้ตรวจสอบย้อนหลัง

วันและเดือนของงาน Points และคำขอแลกรางวัลอ้างอิงเขตเวลา `Asia/Bangkok` เพื่อให้รายการช่วงหลังเที่ยงคืนของไทยไม่ถูกนับย้อนเข้าเดือน UTC ก่อนหน้า

### สูตรและเพดานหลัก

| รายการ | กติกาเริ่มต้น |
| --- | --- |
| ผลประเมินประจำเดือน | ต้องได้อย่างน้อย 70 คะแนน; `(คะแนนรวม − 60) × 6`; สูงสุด 240 Points ต่อเดือน |
| Points จากงานที่ผ่านหลักฐาน | รวมไม่เกิน 420 Points ต่อเดือน และให้ครั้งเดียวต่อแหล่งงาน |
| เข้างานตรงเวลา | +5 Points ต่อวัน สูงสุด 22 วัน หรือ 110 Points ต่อเดือน |
| ส่งก่อนกำหนด / ตรงกำหนด | +25 / +15 Points; โบนัสกำหนดส่งรวมไม่เกิน 80 Points ต่อเดือน |
| โบนัสพิเศษ / เควสต์ | +50 / +75 Points ต้องมีหลักฐาน และแต่ละประเภทไม่เกิน 2 ครั้ง/เดือน |
| Points บวกมาตรฐานนอกผลประเมิน | รวมไม่เกิน 900 Points ต่อเดือน |
| Points ลบ | รวมไม่เกิน 200 Points ต่อเดือน; ลาที่อนุมัติแล้ว 0 Points |
| การแลกรางวัล | ไม่เกิน 2 ครั้ง/เดือน เว้นอย่างน้อย 7 วัน ยอดคงเหลือต้องไม่ติดลบ และต้องรับทราบกติกา Points ฉบับปัจจุบันก่อน |

ตัวอย่าง: คะแนนประเมินรวม 85 คะแนน ได้ `(85 − 60) × 6 = 150` Points

### Points ตามประเภทงานและความสำคัญ

Points จะเข้าหลังผู้มีสิทธิ์อนุมัติหลักฐานแล้วเท่านั้น หากชนเพดาน ระบบยังปิดงานได้แต่จะไม่ให้ Points บางส่วน

| ประเภท | ทั่วไป | ปานกลาง | สำคัญ | เร่งด่วน |
| --- | ---: | ---: | ---: | ---: |
| งาน | 10 | 20 | 35 | 50 |
| รีเควสต์ | 15 | 25 | 40 | 60 |
| ภารกิจ | 40 | 60 | 90 | 120 |

รายการลบเริ่มต้น ได้แก่ มาสาย −20, ขาดงานที่ตรวจสอบแล้ว −120, งานผิดพลาดพร้อมหลักฐาน −40, ใบเตือน −150 และผิดกฎ −100 โดยรายการวินัยทำได้เฉพาะ HR หลังตรวจข้อเท็จจริง ไม่ใช้ Points แทนกระบวนการวินัยหรือสิทธิอุทธรณ์ และหัวหน้าให้หรือหัก Points ตนเองไม่ได้

| มื้อพิเศษกับทีม | 1,200 Points |

ระบบตรวจยอดคงเหลือ สต็อก จำนวนครั้ง ช่วงพัก และการรับทราบกติกาก่อนสร้างคำขอแลก จากนั้น HR เปลี่ยนสถานะตามลำดับ `รออนุมัติ → อนุมัติ → ส่งมอบแล้ว` หรือยกเลิกได้ก่อนส่งมอบ การหัก Points ใช้รายการใน ledger และการยกเลิกจะคืน Points กับสต็อกเพียงครั้งเดียวด้วยรายการย้อนกลับแทนการลบประวัติเดิม

## โครงสร้างข้อมูล

ข้อมูลหลักเก็บใน Cloudflare D1 ผ่าน Drizzle ORM และไฟล์เอกสารเก็บใน Cloudflare R2

- `employees`, `employee_profiles`, `hr_profiles` — ทะเบียนพนักงาน ข้อมูลส่วนตัว การจ้าง และค่าตอบแทน
- `user_accounts`, `notification_reads` — บัญชี บทบาท การผูกพนักงาน และสถานะอ่านการแจ้งเตือนรายผู้ใช้
- `evaluations`, `skill_achievements`, `talent_actions` — ผล KPI/สกิล ระดับที่ยืนยันแล้ว เงินเพิ่ม และแผนพัฒนา
- `attendance_records` — เวลาเข้า–ออก มาสาย ขาดงาน วันลา และประวัติการอนุมัติ
- `projects`, `work_items`, `work_submissions` — โปรเจกต์ งาน ความคืบหน้า หลักฐาน และผลตรวจ
- `point_ledger`, `point_events`, `point_mutation_claims`, `point_cap_claims` — ยอดเคลื่อนไหว เหตุการณ์ หลักฐาน snapshot กฎที่ใช้ และตัวล็อกเพดาน Points
- `rewards`, `reward_redemptions`, `reward_redemption_claims` — แคตตาล็อก สต็อก คำขอแลก และตัวกันคำขอหรือการตัดสต็อกซ้ำ
- `organization_policies`, `organization_policy_publish_claims` — เนื้อหา เวอร์ชัน ช่วงมีผล ขอบเขต กติกา hash และตัวกันการประกาศชนกัน
- `policy_acknowledgements` — หลักฐานการรับทราบที่ผูกพนักงาน บัญชี เวอร์ชัน และ content hash
- `application_documents`, `employment_contracts` — เอกสารสมัครงาน สัญญาหลายเวอร์ชัน คำยินยอม และลายเซ็นอิเล็กทรอนิกส์

Migration ล่าสุดที่เกี่ยวข้อง:

- `0008_spotty_trauma.sql` เพิ่ม `user_accounts`
- `0009_easy_wong.sql` เพิ่ม `notification_reads`
- `0010_dry_blue_blade.sql` เพิ่ม `organization_policies`, `policy_acknowledgements` และ index สำหรับค้นหา/กันการรับทราบซ้ำ
- `0011_same_iceman.sql` เพิ่ม snapshot นโยบายในรายการ Points, version ของสต็อก และ claim สำหรับกันการประกาศหรือแลกรางวัลชนกัน
- `0012_common_christian_walker.sql` เพิ่มล็อกกลางของเพดาน Points ต่อพนักงาน/เดือน, ฟิลด์ป้องกันการประกาศร่างล้าสมัย และดัชนีห้ามหลักฐานรอตรวจซ้ำ
- `0013_bangkok_reward_month.sql` เป็น migration marker สำหรับการเปลี่ยนตัวตรวจเดือนรางวัลเป็นเวลาไทย
- `db/initialize.ts` สร้างตาราง ดัชนี และ trigger ป้องกัน race condition ตอนเริ่มระบบ โดยเก็บ trigger แบบ `BEGIN/END` ไว้นอกไฟล์ migration เพื่อให้ใช้กับตัวรัน migration ของ Sites/D1 ได้ ส่วนฐานข้อมูลเดิมอัปเกรดผ่าน migration ตามลำดับ

ไฟล์ `lib/kpi-data.ts` เป็นแหล่งเทมเพลตตำแหน่ง KPI สมรรถนะ AI Mastery กติกา Points นโยบายเริ่มต้น และรางวัลเริ่มต้น ส่วน `drizzle/` และ `drizzle/meta/` เก็บ migration กับ snapshot ของสคีมา

## เปิดใช้จริงอย่างปลอดภัย

Production จะ **ไม่เติมข้อมูลตัวอย่างอัตโนมัติ** ค่าเริ่มต้นของ `PEOPLE_PULSE_ENABLE_DEMO_DATA` คือปิด และควรเปิดเป็น `true` เฉพาะฐานทดลองที่แยกจากข้อมูลจริงเท่านั้น ข้อมูลตัวอย่างที่เคยอยู่ใน D1 เดิมจะไม่ถูกลบเอง ให้สำรองและล้างหรือย้ายโดยได้รับการยืนยันจากเจ้าของข้อมูลก่อน

หน้า **ผู้ใช้งานและสิทธิ์** มี Launch Readiness Center ตรวจ 6 เรื่อง: ข้อมูลตัวอย่าง, พนักงานจริง, กฎที่ผ่านการทบทวน, บัญชีที่ผูกกับโปรไฟล์, การเข้าใช้ครั้งแรก และเส้นทางเอกสาร/หลักฐานจริง ระบบนี้แสดงสถานะเท่านั้นและไม่ลบข้อมูลแทน HR

ลำดับแนะนำสำหรับ pilot ทีม Growth-Commerce 8 คน:

1. สำรอง D1/R2 และยืนยันว่าจะล้างหรือเก็บฐาน demo แยก
2. นำเข้ารายชื่อ อีเมล ตำแหน่ง ผู้จัดการ และค่าตอบแทนจริง
3. ให้ HR/ฝ่ายกฎหมายแก้แม่แบบกฎองค์กร แล้วประกาศเวอร์ชันจริง
4. สร้างบัญชีในแอปด้วยอีเมลเดียวกับบัญชี ChatGPT และเพิ่มอีเมลเหล่านั้นเป็นผู้ดูเว็บไซต์แบบ private/custom
5. ให้ HR 1 คน หัวหน้า 1 คน และพนักงาน 2–3 คนทดสอบมอบหมายงาน → ส่งหลักฐาน → ตรวจ → ได้ Points → แลกรางวัล รวมถึงอ่านและลงนามสัญญา
6. ทดลอง 3–5 วัน ตรวจข้อมูลและสิทธิ์ แล้วจึงเชิญสมาชิกที่เหลือ

การเปิดทั้งบริษัทต้องเพิ่มตำแหน่ง KPI สกิล และกรอบเงินเดือนของ Telesales, Accounting และทีมผลิต/แพ็ก/ขนส่งก่อน เพราะเวอร์ชันปัจจุบันออกแบบ pilot สำหรับทีม Growth-Commerce 8 ตำแหน่ง

## เริ่มใช้งานในเครื่อง

ต้องใช้ Node.js 22.13 ขึ้นไป

```bash
npm install
npm run dev
```

สร้างและตรวจระบบ:

```bash
npm run build
npm test
npm run lint
```

สร้าง migration หลังแก้สคีมา:

```bash
npm run db:generate
```

การเผยแพร่ผ่าน OpenAI Sites จะผูก D1 binding ชื่อ `DB` และ R2 binding ชื่อ `FILES` ตาม `.openai/hosting.json`
