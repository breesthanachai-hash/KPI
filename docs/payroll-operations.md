# People Pulse — คู่มือเงินเดือนและแผนดูแลระบบ

## สิ่งที่เพิ่มในรอบนี้

แยกเงินเดือนออกจาก dashboard เดิมเป็นโมดูลเฉพาะ (`payroll-center`, API payroll, calculation, benefits, attendance, mail) เพื่อลดความเสี่ยงเมื่อแก้ฟีเจอร์อื่น ข้อมูลพนักงานและยอดเงินเดือนเดิมไม่ถูกลบหรือปรับลดเอง

- HR/Admin จัดร่างได้ เจ้าของ `user-owner` อนุมัติและส่งอีเมล พนักงานเห็นเฉพาะสลิปของตัวเอง หัวหน้าไม่มีสิทธิ์ดูเงินเดือนทีม
- ค่าแรงเป็นจำนวนเต็มสตางค์ ปัดครึ่งขึ้นแต่ละรายการ รายเดือนแบ่ง 1–5 วิค เศษสตางค์อยู่ในวิคสุดท้าย และล็อกฐานเงินเดือน/จำนวนวิคทั้งเดือน
- รายวันกรอกวันได้รับค่าแรงจริง รายชั่วโมงและ OT กรอกหน่วย/อัตราที่บริษัทอนุมัติ ไม่มีการเดาตารางงานหรือหักวันลาอัตโนมัติ
- รายเดือนรวมวันหยุดได้รับค่าแรง 4 วันแล้ว ไม่บวกเงินวันหยุดซ้ำ วันจ่ายแต่ละวิคและสิทธิ์วันหยุดของรายวันต้องเจ้าของยืนยัน
- คอมมิชชันเป็น % ยอดขายที่ตรวจแล้ว บวกส่วนคงที่ได้ ต้องใส่เลขอ้างอิง ห้ามเลขอ้างอิงเดิมซ้ำสำหรับคนเดิม
- เงินเพิ่มสกิลกำหนดยอดและเดือนเริ่ม–สิ้นสุด เช่น 500 บาท ก.ย.–พ.ย. รวม 3 เดือน โบนัสเควสเชื่อมรายการสำเร็จจริงและจ่ายเดือนเดียว ไม่แปลง Points เป็นเงิน
- สกิลเก่าที่เคยบวกเข้าเงินเดือนยังเก็บไว้และไม่ให้นำมาบวกซ้ำ การยืนยันสกิลใหม่ไม่เพิ่มฐานเงินเดือนเอง ให้เจ้าของกำหนดเงินเพิ่มมีระยะเวลา
- เบี้ยขยัน 300 บาทอ้างอิงเดือนก่อนหน้า: ทำงานครบเดือน มีวันเริ่มงานถูกต้อง ระบุวันหยุดจริง 4 วัน มีเวลาเข้างานครบวันทำงาน และไม่มีขาด/ลา/สาย (รวมลาที่อนุมัติ) ข้อมูลไม่ครบไม่เสนอเงิน ต้องตรวจทุกเดือนใหม่ และจ่ายได้ครั้งเดียวในเดือนถัดไป

## ขั้นตอนปฏิบัติก่อนจ่ายจริง

1. เปิดเมนู “เงินเดือน / คอมมิชชัน” สร้างรอบ เลือกเดือนและช่วงวันที่ไม่เกิน 32 วัน
2. เลือกพนักงาน ตรวจชื่อ อีเมล และค่าแรงเต็มเดือน/รายวันตามข้อตกลงจริง ไม่ใช้ค่าตั้งต้นโดยไม่ตรวจ
3. ระบุจำนวนวิค/วิคที่ สำหรับรายเดือน เลือกเงินเพิ่มประจำเดือนในวิคเดียวที่ต้องการจ่าย
4. กรอก OT ยอดขาย % คอม เลขอ้างอิง เงินเพิ่ม และรายการหักที่ฝ่ายบัญชีตรวจแล้ว
5. ภาษี/ประกันสังคมยังเป็นยอดกรอกเอง ค่าเริ่มต้น 0 ไม่ใช่การรับรองว่าไม่ต้องหัก บันทึกกติกาและผู้ตรวจในร่าง
6. กดบันทึกเพื่อคำนวณและดึงเงินเพิ่มล่าสุด ตรวจรายรับ รายการหัก สุทธิ และสถานะเบี้ยขยันทีละคน
7. เจ้าของตรวจรายชื่อ/อีเมล/ยอดทั้งหมดแล้วอนุมัติ สลิปจะล็อก หากเป็นวิคถัดไปเดือนเดิมให้ยืนยันเป็นรอบเพิ่มเติม ระบบยังกันวิคและสิทธิ์เดิมซ้ำ
8. เปิดสลิป พิมพ์หรือบันทึก PDF ผ่านเบราว์เซอร์ โอนผ่านช่องทางบริษัทเอง แล้วบันทึก “จ่ายแล้ว” พร้อมวันและเลขอ้างอิง ระบบนี้ไม่โอนเงิน
9. ส่งอีเมลเฉพาะสลิปที่อนุมัติแล้ว อีเมลมีลิงก์เข้าสู่ระบบ ไม่ใส่ยอดเงิน/ข้อมูลเงินเดือนในอีเมล

## Gmail ของบริษัท — ยังต้องเชื่อมก่อนส่งจริง

ผู้ส่งที่อนุญาต: `maechalao2333@gmail.com` ไม่ใช้รหัสผ่านบัญชี Gmail และไม่ใช้สิทธิ์ ChatGPT ในการล็อกอิน People Pulse

ตั้งค่า OAuth client ใน Google Cloud ที่เปิด Gmail API และให้เจ้าของ Gmail อนุญาต scope `https://www.googleapis.com/auth/gmail.compose` พร้อม offline access เก็บค่าใน hosted environment เท่านั้น:

- `PEOPLE_PULSE_GMAIL_CLIENT_ID`
- `PEOPLE_PULSE_GMAIL_CLIENT_SECRET` (secret)
- `PEOPLE_PULSE_GMAIL_REFRESH_TOKEN` (secret)
- `PEOPLE_PULSE_CANONICAL_ORIGIN` ต้องเป็น HTTPS origin ของเว็บไซต์จริง

ห้าม commit token ลง Git หรือใส่ในข้อมูลสำรอง และไม่ส่ง token ในแชต การมีค่าครบหมายถึง “ตั้งค่าแล้ว” ไม่ใช่ “ผ่านการส่งจริงแล้ว” ต้องทดสอบด้วยสลิปที่เจ้าของอนุมัติและอีเมลทดสอบที่ได้รับอนุญาตก่อนเปิดใช้งานจริง

Gmail: สร้างร่าง บันทึกรหัสร่างในฐานข้อมูล แล้วจึงส่ง ข้อมูล MIME/ผู้รับถูกตรึงจากสลิป ระบบบันทึกจุดเริ่มส่งก่อนเรียก Gmail ถ้าหลุด/หมดเวลาให้สถานะ “ต้องตรวจสอบ” และไม่ส่งซ้ำอัตโนมัติ ตรวจโฟลเดอร์ Sent/Drafts และ Message-ID ของสลิปก่อนกู้สถานะ เจ้าของไม่ควรลบ/แก้ร่างที่ระบบสร้างระหว่างกำลังส่ง

“บริการอีเมลรับแล้ว” คือ Gmail API รับคำขอ ไม่ใช่ยืนยันเข้ากล่องจดหมาย ไม่มี scheduler retry เบื้องหลังในรุ่นนี้ กรณีผิดพลาดก่อนเริ่มส่งลองใหม่ได้หลัง 1 นาที สูงสุด 5 ครั้ง กรณีเริ่มส่งแล้วต้องตรวจสอบก่อน ไม่มีปุ่มข้ามการป้องกันส่งซ้ำ

อ้างอิง: [Gmail drafts lifecycle](https://developers.google.com/workspace/gmail/api/guides/drafts), [sending MIME](https://developers.google.com/workspace/gmail/api/guides/sending), [OAuth offline access](https://developers.google.com/identity/protocols/oauth2/web-server#offline)

## ความปลอดภัยและการแก้ไขย้อนหลัง

- ทุกการแก้ร่าง/อนุมัติต้องตรง revision ล่าสุด การแก้พร้อมกันแพ้หนึ่งรายการด้วย 409
- สลิป ประวัติอนุมัติ สิทธิ์เงินเพิ่ม และประวัติใช้สิทธิ์ล็อกด้วยฐานข้อมูล ไม่มีการลบข้อมูลการเงินตามการลบพนักงาน
- การอนุมัติและการสร้างสลิป/สิทธิ์ทั้งหมดเป็น batch เดียว ล้มเหลวแล้ว rollback ทั้งชุด มี guard ตรวจข้อมูลลงเวลา/วันเริ่มงาน ณ ตอน commit
- ลบร่างทางธุรกิจใช้ “ยกเลิกร่าง” ประวัติยังอยู่ รายการที่อนุมัติแล้วแก้ยอด/ยกเลิกย้อนหลังไม่ได้ในรุ่นนี้ หากจ่ายขาดทำรอบเพิ่มเติมที่ไม่มีฐานเงินเดือนซ้ำ หากจ่ายเกินต้องให้ฝ่ายบัญชีจัดการและพัฒนา adjustment/credit workflow ก่อน ห้ามแก้ฐานข้อมูลตรง
- การกำหนดเงินเพิ่มเป็น immutable grant ยังไม่มีการเพิกถอน/แก้ระยะเวลาของ grant ใน UI ต้องตรวจจำนวนและช่วงเดือนก่อนยืนยัน
- ผู้ลาออกไม่สามารถล็อกอินเดิม ให้ HR ส่งมอบเอกสารตามขั้นตอนบริษัท ไม่คลายสิทธิ์ทั้งระบบเพื่อให้เข้าถึงสลิป

## สำรองและกู้คืน

ส่งออกข้อมูลสำรองผ่านศูนย์ตั้งค่าระบบก่อนเปลี่ยน schema ข้อมูลเงินเดือน/ประวัติรวมใน backup แต่ความลับ Gmail อยู่ใน environment แยกต่างหาก จัดเก็บสำรองในที่จำกัดสิทธิ์

ตัวนำเข้าหยุดใช้ `INSERT OR REPLACE` แล้ว เพราะอาจลบ/แทนที่ประวัติการเงิน ต้องใช้ฐานข้อมูลว่างที่แยกจากระบบจริงและใช้ migrations ล่าสุด โดยยังไม่เริ่มแอป/ยังไม่ติดตั้ง runtime payroll guards ตัวนำเข้าตรวจว่าไม่มีข้อมูลก่อนเขียน ไม่รองรับ merge หรือเขียนทับฐานข้อมูลจริง ถ้ากู้บางส่วนไม่ครบให้หยุดตรวจ ไม่ลองเขียนทับซ้ำ

ข้อจำกัดสำคัญ: export อ่านตารางแยกกัน ไม่ใช่ transaction snapshot ข้ามทุกตาราง ให้หยุดการแก้ข้อมูลช่วงสำรองก่อนกู้คืนที่ต้องการความสอดคล้องสูง การทดสอบรอบนี้ไม่ได้กู้ backup บริษัทจริงเข้าฐานข้อมูลใหม่ ต้องทำ restore rehearsal แยกก่อนกำหนด RPO/RTO อย่างเป็นทางการ

## แผนต่อยอดตามลำดับความสำคัญ

1. ก่อนส่งจริง: เชื่อม Gmail, ยืนยันวันวิค/สิทธิ์วันหยุดรายวัน, ตรวจ reconciliation กับวิธีคิดของบัญชี 1 รอบ และทดสอบสลิปด้วยผู้รับที่อนุญาต
2. รอบถัดไป: ตารางงาน/วันหยุดแบบปฏิทิน เพื่อลดการกรอก 4 วันที่เอง, ค่าแรงรายคนพร้อมวันที่เริ่มมีผล, วันจ่ายมาตรฐาน และคัดลอกรอบเดิมโดยไม่คัดลอกสิทธิ์ที่จ่ายแล้ว
3. การเงิน: adjustment/credit ที่อ้างสลิปเดิม, เพิกถอน grant เฉพาะงวดอนาคตแบบมี audit, ส่งออกบัญชี/ไฟล์ธนาคารพร้อมตรวจสอบ (ไม่สั่งโอนเอง)
4. ความทนทาน: durable queue สำหรับ delivery ที่ยังไม่เริ่มส่ง, หน้ากู้สถานะอีเมลหลังตรวจ Gmail, alert เมื่อเชื่อม Gmail หลุดหรือมีงานค้าง
5. ดูแลระยะยาว: backup แบบ consistent snapshot + restore rehearsal, เพิ่ม regression tests ทุกครั้งแก้กติกา, แยก dashboard เดิมต่อเป็นโมดูลตามหน้าที่ และ version trigger เมื่อเปลี่ยน guard หลังเผยแพร่
