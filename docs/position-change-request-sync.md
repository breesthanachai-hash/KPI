# คำขอเปลี่ยนตำแหน่งระหว่างเครื่องทดสอบและระบบหลัก

เมนู: **จัดการพนักงาน → คำขอเปลี่ยนตำแหน่ง** (Admin/HR เท่านั้น)

## เปิดใช้โดยไม่กระทบข้อมูลเดิม

1. เก็บสำรองฐานข้อมูลของ environment ปลายทางผ่านขั้นตอนปกติขององค์กรก่อนอัปเกรด อย่านำไฟล์สำรองเข้า Git
2. ใช้ตัวจัดการ migration ของ environment นั้นรัน migration ใหม่ `drizzle/0026_employee_position_change_requests.sql` เพียงครั้งเดียว หลัง migration 0025 ไม่ต้องนำเข้าฐานข้อมูลจากเครื่องทดสอบ ไม่แก้ migration เก่า
   - Sites จะใช้ migration ที่บรรจุในชุด build เมื่อผู้ดูแลสั่งเผยแพร่ในอนาคต งาน PR นี้ไม่เผยแพร่และไม่รัน migration บนข้อมูลจริง
   - Local: ใช้ config D1 ของเครื่องนั้นกับ `wrangler d1 migrations apply DB --local --config <config ของเครื่องนั้น>` โดยตรวจว่า migrations_dir ชี้โฟลเดอร์ drizzle และเป็นฐานข้อมูลทดสอบที่ถูกต้องก่อน ห้ามใช้ --remote โดยไม่ตั้งใจ
   - หากยังไม่รัน migration หน้าใหม่จะแจ้งระบบยังไม่พร้อม ไม่สร้างตารางคำขอทับเอง
3. เครื่องทดสอบไม่ต้องเพิ่มค่าตั้งค่าใด ค่าเริ่มต้น **ปิดการอนุมัติและปฏิเสธ**
4. เฉพาะระบบหลัก: ตั้ง runtime environment `PEOPLE_PULSE_POSITION_REQUEST_APPROVAL_ENABLED=true` แล้วเริ่มแอปใหม่/เผยแพร่ตามกระบวนการของระบบหลัก ค่านี้เป็นตัวเปิดความสามารถ ไม่ใช่รหัสลับ แต่ต้องควบคุมโดยผู้ดูแลระบบฝั่งเซิร์ฟเวอร์ ไม่รับค่าจากไฟล์คำขอหรือเบราว์เซอร์
5. คงบัญชี รหัสผ่าน pepper และ environment เดิมทั้งหมด ไม่ใช้ bootstrap/reset หรือคัดลอก .dev.vars จากอีกเครื่อง

คำว่า “เครื่องหลัก” หมายถึง environment ที่ผู้ดูแลเปิดค่าข้างต้น ไม่ได้ผูกกับชื่อคอมพิวเตอร์หรือค่าที่ผู้ใช้ส่งจากเบราว์เซอร์ อย่าเปิดค่านี้ในเครื่องทดสอบ ถ้าระบบหลักอยู่บนเว็บ ให้ตรวจและอนุมัติผ่านบัญชี HR/Admin ของเว็บนั้น

## ขั้นตอนทำงาน

1. เครื่องทดสอบ: เลือกพนักงาน ระบุกรอบตำแหน่งใหม่/ชื่อเฉพาะและเหตุผล กด **สร้างคำขอเท่านั้น** ข้อมูลพนักงานยังไม่เปลี่ยน
2. ส่งออกคำขอรออนุมัติเป็น JSON ชุดละ 100 รายการ หากมีมากกว่านั้นใช้ **ส่งออกคำขอชุดถัดไป** เก็บไฟล์ในช่องทางจำกัดสิทธิ์ ไม่แนบรหัสผ่านหรือข้อมูลลับในเหตุผล
3. ระบบหลัก: เลือกไฟล์ จะเห็นตัวอย่างตำแหน่งเดิม/ใหม่ ผู้ร้องขอตามไฟล์ รายการซ้ำและ conflict ก่อนนำเข้า การเลือกไฟล์ยังไม่บันทึกอะไร
4. กด **นำเข้าเป็นคำขอรออนุมัติ** เพื่อเก็บข้อเสนอเท่านั้น ไม่อนุมัติอัตโนมัติ
5. HR/Admin กดตรวจรายคน อ่านตำแหน่งและกรอบ KPI ใหม่ ยืนยันการเปลี่ยนข้อมูลจริง แล้วอนุมัติ หรือระบุเหตุผลเพื่อปฏิเสธ
6. ดูผลในรายการคำขอ และดู **พนักงานทั้งหมด → ประวัติการแก้ไขโปรไฟล์** สำหรับการเปลี่ยนที่อนุมัติ มีผู้อนุมัติ เวลา ค่าเดิม/ใหม่ และรหัสคำขอ

การเปลี่ยน role_id เปลี่ยนกรอบ KPI ของพนักงานและข้อมูลการจัดกลุ่มงานที่อิงกรอบนั้น แต่ไม่แก้บทบาทหรือสิทธิ์บัญชีใน user_accounts ไม่เปลี่ยนเงินเดือน ไม่ผูกงานรายวันใหม่ และไม่แก้คะแนนประเมินย้อนหลัง

## ความปลอดภัยและ conflict

- ตารางคำขอแยกจาก employees; เก็บ snapshot ของ role/title และ updated_at เดิม การนำเข้าไม่แก้พนักงาน
- ตอนอนุมัติตรวจ employee_id, สถานะ active, role เดิม, ชื่อตำแหน่งเดิม และ updated_at อีกครั้งใน transaction เดียวกับ audit/การเปลี่ยนตำแหน่ง ถ้าค่าใดต่างกันจะ rollback ทั้งชุดและคง pending
- หาก conflict ให้ปฏิเสธพร้อมหมายเหตุ หรือสร้างคำขอใหม่จากข้อมูลล่าสุด ห้ามแก้ไฟล์เพื่อหลบ conflict
- การอนุมัติซ้ำหรืออนุมัติหลังปฏิเสธไม่ทำงาน ไม่รองรับอนุมัติรวมหลายรายการ
- ใช้ employee_position_events เดิมสำหรับการเปลี่ยนชื่อ และ employee_profile_audit เดิมสำหรับค่าเดิม/ใหม่ของชื่อและ role_id ไม่มีระบบประวัติซ้ำอีกชุด
- ไฟล์ส่งออกใช้รายการฟิลด์ที่อนุญาตเท่านั้น ไม่อ่านตาราง credentials/sessions, ไม่ส่ง source_fingerprint และไม่ส่ง environment ไฟล์นำเข้าที่มีฟิลด์เกินหรือสถานะอื่นถูกปฏิเสธ
- ข้อมูลผู้ร้องขอจากไฟล์เป็นเพียงแหล่งอ้างอิงที่ยังไม่ยืนยัน ไม่ใช้เป็นสิทธิ์อนุมัติ บันทึกผู้นำเข้าและผู้อนุมัติจาก session ของระบบหลัก
- รหัสคำขอเดิม+เนื้อหาเดิมนำเข้าซ้ำได้โดยข้าม ไม่คืนสถานะเป็น pending; รหัสเดิม+เนื้อหาต่างกันจะถูกปฏิเสธทั้งชุด
- จำกัดไฟล์ 256 KB / 100 คำขอ ตรวจสิทธิ์ก่อนอ่านไฟล์ และรักษา same-origin gate ของระบบเดิม
- ฟีเจอร์ไม่เขียน user_accounts, auth_credentials, auth_sessions หรือ token และไม่เปลี่ยน environment
- ลบทางเดิน reset Admin แบบ localhost อัตโนมัติที่ยังอยู่ในสาขา GitHub ฐานออกด้วย โดยไม่เปลี่ยนรหัสผ่านที่เก็บไว้

## ตรวจสอบ

```sh
npm run build
npx tsc --noEmit --incremental false
npm run lint
node --test tests/*.test.mjs
```

เทสต์คำขอใช้ SQLite ในหน่วยความจำเท่านั้น ครอบคลุมการส่งข้ามเครื่อง อนุมัติ/ปฏิเสธ conflict และ race, rollback, สิทธิ์, export allowlist, ไฟล์ซ้ำ และประวัติเดิม ไม่ใช้ฐานข้อมูลจริง

ข้อควรทราบก่อน merge/deploy: สาขานี้อิง GitHub codex-wip-settings ไม่ใช่ต้นฉบับ Sites live โดยตรง แพตช์ dependency ความปลอดภัยที่เผยแพร่บน Sites ก่อนหน้านี้ยังไม่ได้อยู่ใน GitHub ฐาน จึงไม่ได้รวม dependency upgrade ที่ไม่เกี่ยวกับงานคำขอใน PR นี้ ควรรวมแพตช์นั้นก่อนเผยแพร่ GitHub branch นี้เป็นเว็บจริง
